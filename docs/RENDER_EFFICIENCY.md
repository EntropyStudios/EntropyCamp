# 前端渲染排查（2026-11-19）

## 结论与边界

剪贴板页面没有 canvas，只加载 clipboard-core、work-history-core、state-client 和 clipboard 脚本；其 rAF 只用于交互过渡和聚焦，没有常驻逐帧循环。主页默认卡片模式同样为 0 canvas。打开过星际模式不等于剪贴板页还在渲染星球。

主页确有持续动画：圣体钟的昆虫与摆锤、大本钟的节拍与报时、天文钟的机关，以及可选的星际场景。这些本身有正常 GPU 开销。此前 WebGL 上下文重复创建的问题已有生命周期约束，本次 500 次元数据更新、结构变更、隐藏恢复和销毁回归仍通过：一个 renderer，销毁时 context loss，资源回到基线。测试不能排除所有驱动或长时运行泄漏。

整机观察时同时有 OBS、桌面合成器和多个 Python GPU 进程；其中一个 Python 进程约占 1460 MiB。整机 GPU 利用率、显存、功耗不能直接归因于 EntropyCamp，也不作为本次优化的收益指标。

## 已减少的工作

- 布拉格钟和伯尔尼钟：机关静止期间每秒更新一次，整点/刻钟表演自动恢复至最高 60 Hz。指针 CSS 过渡、装饰动画继续运行。圣体钟、大本钟的连续机械动画保持最高 60 Hz。
- 钟面自定义属性改写到对应 SVG，不再让四个复杂 SVG 子树都继承每帧变化；相同属性值不重复设置。圣体钟的辅助时间文字也只在改变时更新。
- 卡片模式的背景没有动态内容，因此保留底色、渐变、高光、阴影，移除每张卡的 backdrop blur 和常驻 will-change。布局过渡时才临时声明 will-change，结束后移除。
- 后台隐藏页仍停掉名钟 JS 和三维循环，新增帧入口保护避免隐藏瞬间已经排队的回调重新开启循环。未增加滚出视口暂停逻辑。

## 可重复验证

`test_clock_efficiency.py` 用实际 scheduler 和模拟 240 Hz 的计时队列运行 10 秒。优化前，闲置布拉格、闲置伯尔尼与连续机关均更新 601 次；优化后，闲置钟面约 11 次，连续机关仍约 601 次。该指标是 JS 钟面更新数量，不能换算为整机 GPU 或电耗降幅。

同一测试确认每时刻最多一个计时器或 rAF、停止后队列清空；600 次不变属性请求只产生一次样式设置，动态值仍更新到正确 SVG。

全量 unittest 共 176 项通过；浏览器确认优化后圣体钟显示、卡片排版正常，卡片页 0 canvas，无前端错误。浏览器已打开的旧页面需刷新才加载新代码。
